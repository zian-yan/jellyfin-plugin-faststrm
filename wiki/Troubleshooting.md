# 排障

排查前先确认三件事：条目是不是 `.strm`、当前是**有流**还是**无流**、控制台里的三个策略开关处于什么状态。播放模式与开关的对应关系见 [播放模式：有流与无流](Playback-Modes)。

> 插件大量诊断信息使用 `Debug` 级别（例如「跳过 ffprobe」），默认日志中看不到。需要时在 **控制台 → 日志** 中把 `FastSTRM` 的日志级别调为 Debug 再复现。

---

## 起播仍然要等几秒

| 可能原因 | 确认方式 | 处理 |
| :--- | :--- | :--- |
| 该条目已是有流，等待的是真实拉流而非探测 | 控制台统计中「已有流信息」含该条目；日志无 `Skipping ffprobe` | 属源站速度问题，与插件无关；换源或优化网络 |
| 「未探测的 STRM 文件也跳过探测」被关闭 | 配置页开关状态 | 重新开启，无流条目恢复秒开 |
| 条目不是 `.strm`（如 `.mkv` 内嵌、或改过扩展名） | 检查文件扩展名 | 仅 `.strm` 生效，其余类型走原生管线 |
| 插件未生效 | **控制台 → 插件** 中 FastSTRM 是否启用 | 确认 DLL 在 `plugins/FastSTRM/` 下并重启 Jellyfin |

---

## 进度条没有总时长 / 看不到码率与轨道 / 无法切字幕音轨

条目处于无流状态（`RunTimeTicks` 缺失）。这是「跳过探测」的预期代价，不是故障。

处理方式，按代价从低到高：

1. 开启**后台补探测** —— 该条目下次播放后自动补齐；
2. 跑一次**增量探测** —— 批量补齐所有无流条目；
3. 长期方案：勾选**入库自动探测**，避免新条目继续落入无流状态。

---

## 一开播就被标记为已观看

插件已通过 `PlaybackStateInterceptor` 拦截 Jellyfin「无时长即视为已看完」的判定，正常情况下不应再出现。

若仍出现，依次检查：

- 该条目是否 `SupportsPositionTicksResume = false`（插件只接管支持进度续播的条目）；
- 是否有其他插件或自定义脚本直接写入 `UserData`，绕过了 `IUserDataManager`；
- 日志中是否完全没有 `Preserving playback position` 记录 —— 若没有，说明该次上报未进入插件接管逻辑。

---

## 安装/更新插件时报 504 / 下载失败

```
System.Net.Http.HttpRequestException: Response status code does not indicate success: 504 (Gateway Time-out).
   at Emby.Server.Implementations.Updates.InstallationManager.PerformPackageInstallation(...)
```

这是 **Jellyfin 从 GitHub 下载 `FastSTRM.zip` 失败**，与插件本身无关。常见于新版本刚发布的几分钟内：GitHub 的下载节点对新上传的资产还没完成回源，会短暂返回 504，重试即可恢复（本地实测：连续 3 次 504，约 10 分钟后稳定 200）。

处理：

1. 等 5–10 分钟后在 **控制台 → 插件 → 目录** 里重试更新；
2. 仍失败则手动安装：下载 `FastSTRM.dll`（Release 页的单个 dll 通常比 zip 先恢复），放到 `<插件目录>/FastSTRM/FastSTRM.dll`，重启 Jellyfin；
3. 若长期 504，多半是本机到 GitHub 的链路问题，可给 Jellyfin 容器配置代理后再试。

> 判断包是否完好：`FastSTRM.zip` 的 md5 应与 `manifest.json` 里该版本的 `checksum` 一致。不一致才是包的问题，504 不是。
>
> 资产被重新发布过时 `checksum` 会变。若安装报 **校验和不匹配（checksum mismatch）**，说明 Jellyfin 缓存的是旧版插件目录数据：在 **控制台 → 插件 → 目录** 点「刷新」（或重启 Jellyfin）后再装一次即可。

## 文件大小只有几百字节

媒体信息页显示的大小在 100～300 字节上下，说明条目里存的还是**`.strm` 文本文件本身的大小**——Jellyfin 探测 `.strm` 时探测对象就是这个文件，ffprobe 也报不出远端真实长度（HTTP 流通常是 `size=N/A`）。

补全远端大小没有开关（3.6.1 起配置页只保留请求超时），但**只有三条探测链路会触发**，其余场景（取源 PlaybackInfo、浏览详情页、「官方探测」/「不补探测」策略）一律不请求流地址：

1. **入库自动探测**（`Strm入库自动探测` 开启时）：新条目入库即补；
2. **起播后补探测**（「跳过探测 · 后台补探测」策略）：已有流信息但缺大小的条目只发一次头部请求，不重跑 ffprobe，也不会因停播被取消；
3. **手动增量 / 全量探测**：想一次性修好历史条目，控制台启动 **增量探测**（只对缺大小的条目发头部请求），等价于 `POST /FastStrm/Probe/Start?mode=Incremental`；需要全部覆盖用 **全量探测**（`mode=Full`）。

默认配置下 `Strm入库自动探测` 与「后台补探测」都是关闭的，此时只有手动探测会触发补全——这是预期行为，不是功能失效。控制台「缺少文件大小」计数应随探测下降。

> 3.6.0 起补全动作并入后台补探测、增量探测与全量探测，独立的「仅补全文件大小」模式（`mode=SizeOnly`）已移除，旧调用会被拒绝。

仍是旧值的常见原因：

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 计数不下降，日志无 `Wrote the remote size` | 源站不返回 `Content-Length`，且 `Range` 请求被拒 | 换支持长度查询的直链；插件只做一次头部请求，不会下载内容探测 |
| 部分条目正常、部分不动 | 这些 `.strm` 里不是 `http(s)` 绝对地址，或文件为空/多行异常 | 检查 `.strm` 内容：第一行非空且非 `#` 的行必须是完整 URL |
| 刚补全又变回几百字节 | 库扫描重写了 `.strm` 的文件信息 | 下次播放（「跳过探测 · 后台补探测」策略）或下一次入库/增量/全量探测会再次补全；也可手动再跑一次「增量探测」（只补缺大小的条目） |
| 日志 `timed out` / `failed` | 源站响应慢或需要鉴权 | 调大「大小请求超时」（最大 60 秒）；失败条目 10 分钟内不会重复请求 |

> 少于 1 MiB 的记录才会被替换，已有真实大小不会被覆盖。

---

## 日志：`has no stream info and probing was skipped`

```
FastSTRM: <名称> has no stream info and probing was skipped for instant playback. ...
```

这是**提示，不是错误**。含义：该条目为无流，且本次播放没有探测。每个条目只记录一次，不会刷屏。

- 后半句出现 `a background probe in Ns fills in ...` → 后台补探测已生效，无需处理；
- 后半句出现 `background probing is disabled` → 补探测关闭，时长将一直缺失，直到手动跑预探测。

---

## 日志：`produced no stream info` / `retrying in 10s`

```
FastSTRM: Background probe of <名称> produced no stream info (RunTimeTicks=null); retrying in 10s (retry 1/2)
```

补探测拿到响应但没有时长，通常是源站瞬时异常：

- 上游 `.strm` 地址返回 5xx —— 播放器正在打开同一文件，源站限流；
- 302 跳转目标失效或过期；
- 网盘/WebDAV 鉴权过期；
- 探测超时。

插件会按 `10s → 30s` 重试，最多尝试 **3 次**；全部失败后放弃，同一条目 **10 分钟内不再重复探测**，下次播放时重新尝试。

持续出现时先手动 `curl` 一次 `.strm` 内的地址，确认源站本身可用。探测失败不影响播放与进度保存。

---

## 关闭后台补探测后，仍看到探测请求

按可能性排序：

1. **批量预探测正在运行** —— 控制台「执行状态」为运行中；此时单集补探测会被跳过，但批量任务本身在探测；
2. **入库自动探测已开启** —— 新增条目会自动探测一次；
3. **条目已转为有流** —— 有流条目本身不探测，但若刚被其他路径补齐，会看到一次写入；
4. 之前调度的补探测尚未结束（延迟最长 3600 秒）。

---

## 播放已停止，补探测还在继续

- 「播放停止后取消补探测」被关闭（默认开启）；
- 还有其他会话正在播放同一条目 —— 插件会保留补探测，避免影响另一端的体验；
- 该次补探测已进入重试等待，取消信号在其后生效。

---

## 批量探测无法启动

`POST /FastStrm/Probe/Start` 返回 `409 Conflict`，或按钮无响应：

- 已有任务在运行或仍在停止中（`State` 为 `Running` / `Stopping`），需等待回到 `Idle`；
- 停止是协作式的：正在执行的那一条 `ffprobe` 需要先结束，长超时的源站会让「停止中」持续较久。

---

## 配置页部分选项是灰的

这是依赖关系导致的禁用，不是渲染问题：

| 选项 | 启用前提 |
| :--- | :--- |
| 起播后策略 | 「未探测的 STRM 文件也跳过探测」为开启 |
| 补探测延迟（秒） | 起播后策略为「后台补探测」 |
| 播放停止后取消补探测 | 起播后策略为「后台补探测」 |

---

## 探测成功但时长仍缺失

典型的直播型源（HLS 无 `#EXT-X-ENDLIST`、无限流）本身没有总时长，`RunTimeTicks` 无法写入，条目会一直被判为无流。此时秒开正常，但完成判定不可用，属源特性限制，无法通过插件解决。

---

## 文件大小补全没生效，日志出现 `not an allowed stream target`

`.strm` 里的地址是插件**以服务端身份**去请求的，因此受目标策略约束：

| 目标地址 | 行为 |
| :--- | :--- |
| 公网地址 | 允许 |
| 环回 / RFC1918 / CGNAT / IPv6 ULA | **默认允许**，关闭「允许请求内网地址」后拒绝 |
| 链路本地（含 `169.254.169.254`）、组播、未指定、保留段 | **始终拒绝**，无开关 |

排查步骤：

1. 若是内网源（`192.168.*`、`10.*`、`127.*`），确认配置页「允许请求内网地址」为开启；
2. 若是域名，插件在建连时按**解析结果**判定，域名指向内网地址时同样受上表约束；
3. 把日志级别调到 Debug 可看到被拒绝的具体地址（只记录 scheme/host/path，不带签名参数）。

---

## 升级后行为变化

- 3.5.2 起，补全远端大小的请求受目标策略约束，链路本地地址一律拒绝；环回/私网可用开关收紧；
- 3.5.2 起，小于 1 MiB 的真实媒体也能写入大小（接受下限 4 KB），此前这类条目永远补不上；
- 3.3.0 起，无流条目**默认不再后台补探测**（此前默认补齐）。升级后若发现进度条没了总时长，开启「后台补探测」即可恢复；
- 3.1.0 起，无流条目默认直接跳过探测，不再等待 `ffprobe`；
- 配置文件缺字段时按默认值处理，无需手工修改。

完整变更见 [CHANGELOG](https://github.com/zian-yan/jellyfin-plugin-faststrm/blob/main/CHANGELOG.md)。
